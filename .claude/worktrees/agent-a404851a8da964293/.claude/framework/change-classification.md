# Change Classification Taxonomy

**Scope:** used by `/cleanup` to group uncommitted changes, and by `/review` to sanity-check that a diff's actual content matches what its title/message claims. Not a doc about architecture — purely a labeling scheme for git-state analysis.

## Categories

| Category | Signal |
|---|---|
| **Feature** | New endpoint, command/query, entity, or capability that didn't exist before |
| **Bug Fix** | Changes behavior to match already-documented/expected behavior; usually touches a narrow code path |
| **Refactor** | No behavior change; restructures existing code (extraction, renaming internals, layer cleanup) |
| **Rename** | File/type/member renamed with no logic change — should show as a rename in `git status`, not add+delete |
| **Formatting** | Whitespace/ordering/style only — no logic change |
| **Infrastructure** | Docker, CI, DI wiring, hosting/startup config |
| **Configuration** | `appsettings*.json`, `.env*`, connection strings, feature flags |
| **Migration** | EF Core migration files, schema changes |
| **Documentation** | `docs/**`, `README.md`, comments-only changes |
| **Generated** | Build/tool output that shouldn't be hand-edited: `bin/`, `obj/`, EF `*.Designer.cs` migration snapshots, `*.lock.json`, OpenAPI/Swagger snapshot exports |

## Classification rules
1. Classify per file, not per commit — a single logical change may span multiple files in the same category, that's fine.
2. A file touching more than one category (e.g. a feature file that also reformats unrelated lines) is **mixed** — flag it explicitly, don't force it into one bucket.
3. Migration files are always their own category, never bundled into Feature, even when added alongside a feature — they have independent rollback risk.
4. When in doubt between Refactor and Feature: if `git diff` shows added public surface (new method, new endpoint, new field), it's Feature; if it's purely internal restructuring with identical external behavior, it's Refactor.
5. **Generated** files are never merged into another category even if they changed as a side effect of one (e.g. a `*.Designer.cs` snapshot regenerated by a real migration) — call out the pairing (which real change produced this generated diff) rather than hiding the generated file inside that change's group.
