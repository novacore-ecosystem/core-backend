# User Service

**Scope:** User-specific facts and its documented divergences from the [Auth Service](auth-service.md) reference implementation. General patterns live in [04-coding-rules.md](../04-coding-rules.md)/[02-architecture-rules.md](../02-architecture-rules.md) — not repeated here.

## Projects

`User.Domain`, `User.Application`, `User.Infrastructure`, `User.Persistence`, `User.API` — same 5-layer split as Auth.

## Entities

- **UserPaymentMethod** (`User.Domain/Entities/Users/UserPaymentMethod.cs`) — owned child of `User`, a **lightweight reference only**: `PaymentAccountId` (Payment Service's own `PaymentAccount.Id`, unique per row), `DisplayName`, `IsDefault`. UserService never stores a token, masked card number, provider, or any other account/card detail — those are exclusively Payment Service's concern (`src/Services/Payment`, `PaymentAccount`/`PaymentToken`/`CardInformation`). No Application/API surface exists for this entity yet (domain+persistence only). See [payment-service.md](payment-service.md) and [reference/payment-ownership-boundaries.md](../reference/payment-ownership-boundaries.md) for the full responsibility split.

## Ports & routing

Internal `8080` (REST) / `5002` (gRPC server — User is the gRPC *server* here, Auth is the client). Gateway path prefix `/api/user/` (`RequireAuth: false`).

## Routes (Carter endpoints, `User.API/Endpoints/`)

| Method | Route | File | Purpose |
|---|---|---|---|
| POST | `/profiles` | `CreateUser.cs` | Create a user profile (also invoked via gRPC from Auth's registration flow) |
| GET | `/profiles/{userId}` | `GetUser.cs` | Fetch a profile by id |
| GET | `/profiles/current/detail` | `GetUserDetail.cs` | Fetch the current authenticated user's detail |
| PUT | `/profiles/{userId}` | `UpdateUser.cs` | Update a profile |
| POST | `/users/search` | `SearchUsers.cs` | Admin/Root only. Paginated, filterable, sortable search — Elasticsearch-backed since 2026-07-28 (see [reference/search.md](../reference/search.md#user-search)), not Postgres. Keyword search covers full name (First/Middle/Last, case+accent+word-order insensitive), plus `role`/`status`/`phone` filters and `userName`/`email`/`createdAt`/`updatedAt` sorts. `UserCriteriaDefinition`/`BuildingBlock.Criteria` are kept only as the request-shape validator (`SearchUsersValidator`), not the query engine |
| POST | `/users/search/rebuild` | `RebuildUserSearchIndex.cs` | **Requires Admin or Root.** Drops and recreates the Elasticsearch index, repopulates from Postgres. See [reference/search.md](../reference/search.md#user-search) |

## User-specific building blocks (not present in Auth)

- **gRPC server** — `User.API/GrpcServices/UserGrpcServiceImpl.cs` (`UserGrpcService.UserGrpcServiceBase`) exposes:
  - `CreateUserProfile` — thin adapter, dispatches `CreateUserCommand`-equivalent internal event via `ISender`/`IInternalEventDispatcher`, no business logic. Called by Auth's registration flow.
  - `GetUser`/`GetUsers` (single/batch, added 2026-07-28) — User's first read-oriented RPCs. Cache-backed: the handlers explicitly call `IUserProfileDetailCache` (see "User Detail cache" below) instead of `IUserReadService`; `GetUsers` never falls back to a loop of single DB lookups, and never omits a requested id from the response (`found=false` instead, mirroring Inventory's `GetProductsStock` convention). See [reference/grpc.md](../reference/grpc.md).
- **Elasticsearch search** (added 2026-07-28) — `User.Persistence/Contexts/Users/Search/`, mirroring Product's architecture exactly (see [reference/search.md](../reference/search.md#user-search)). The one addition beyond Product's pattern: a custom accent/case-folding analyzer (`user_search_name_analyzer`), since Product's own search only ever needed case-insensitivity.
- **User Detail cache** (added 2026-07-28, redesigned 2026-08-04) — `IUserProfileDetailCache` (`User.Application/Abstractions/Services/`) is an explicit, cache-specific abstraction (`GetByIdAsync`/`GetByIdsAsync`/`InvalidateAsync`), implemented by `UserProfileDetailCache` (`User.Infrastructure/Caching/Users/`, Redis-backed read-through: cache → `IUserReadService` on miss → refresh → return, single and batch). No decorator - `GetUserByIdHandler`/`GetUserDetailHandler`/`GetUsersByIdsHandler` call it directly for reads, and `UpdateUserHandler`/`OnUserDeletionHandler` call `InvalidateAsync` explicitly at the point their write workflow has actually finished (after the transaction commits / after delete succeeds), not automatically off of every persistence call - see [reference/caching.md](../reference/caching.md#no-decorators-for-cache-invalidationrefresh-mandatory-project-wide) for why decorators are disallowed for this. Caches the existing flat `UserReadModel` directly - no separate DTO needed. Invalidated on Update and the real delete path (`OnUserDeletionHandler`, not the dead `DeleteUserCommand`/`DeleteUserHandler` — see "Known issues"). See [reference/caching.md](../reference/caching.md#user-detail-cache-explicit-orchestration-canonical-example).
- **Locale-aware DisplayName** (added 2026-07-28) — `IUserDisplayNameFormatter` (`User.Application/Services/`) composes `FirstName`/`MiddleName`/`LastName` per locale (`vi`-prefixed → Last Middle First; default → First Middle Last), read from `ICurrentLocaleService` (`BuildingBlock.Application`/`BuildingBlock.Infrastructure`, mirrors `ICurrentUserService`, resolves the caller's locale from the `Accept-Language` header — no custom header needed, the frontend already sends it). Never persisted; computed fresh on every `GetUser`/`GetUserDetail`/`SearchUsers` response. gRPC responses use a fixed `"en"` default instead, since a gRPC caller is a service, not an end-user request.
- **Hangfire background jobs** (`User.Infrastructure/BackgroundJobs/BackgroundJobsExtensions.cs`) — User has its own Hangfire storage (`ConnectionStrings:Hangfire` → `user_hangfire_db`) and dashboard at `/hangfire`, wired through the shared `BuildingBlock.Infrastructure` bootstrap (`AddHangfireScheduling`/`AddInboxOutboxCleanupJobs`, same as Auth — see [auth-service.md](auth-service.md#auth-specific-building-blocks-not-shared-with-user)). Currently the only recurring jobs registered are the shared Inbox/Outbox cleanup jobs; User has no service-specific `IRecurringJob` of its own yet.
- **Integration event consumers** — `User.Infrastructure/Messaging/Consumers/UserAccountDeletionIntegrationEventConsumer.cs` (`IIntegrationEventConsumer`, topic `user-service.useraccountdeletionintegrationevent`) dispatches `DeleteUserProfileCommand`. This is the inbound half of the account-deletion flow documented in [reference/events.md](../reference/events.md). Plus two new self-consuming consumers added 2026-07-28 for the search index (`UserProfileCreatedSearchSyncConsumer`, `UserProfileUpdatedSearchSyncConsumer`) — see [reference/search.md](../reference/search.md#user-search).
- **Idempotency handling** — `CreateUserCommandHandler` does check-then-create, then on `SaveChangesAsync` failure re-checks for a concurrent winning write. Necessary because it can be invoked twice for the same user (gRPC call + potential Kafka redelivery). Auth's `RegisterHandler` doesn't need this — registration is a single client-initiated call, not idempotency-sensitive the same way. **If you're writing a handler that can be triggered by both a direct call and an event/gRPC path, follow this pattern, not Register's.**
- **Read-only role cache consumer** — `User.Infrastructure/Caching/RoleCacheReader.cs` (`IRoleCacheReader`) reads the role cache that *Auth* owns and writes (`RoleCacheService`) — a separate cache from the User-owned User Detail cache above, kept unmerged. See [reference/caching.md](../reference/caching.md#cross-service-read-only-consumer).

## Persistence: Read/Write services

User was the reference implementation (Phase 1) for the [persistence Read/Write migration](../refactoring/persistence-refactor-plan.md) — see [conventions/persistence-coding-conventions.md](../conventions/persistence-coding-conventions.md) for the binding standard. **Rewritten 2026-08-04** to follow the identity-model redesign (`User` is now the aggregate root; the old flat `UserProfile` with `Email`/`UserName`/`PhoneNumber`/`Roles` columns was demoted to an owned 1:1 child holding only `PersonalName`/`Birthday`/`Gender`/etc). Handlers inject `IUserReadService`/`IUserWriteService` (`User.Application/Abstractions/Persistence/Users/`), never a repository interface. Both sides return/accept `UserReadModel` (`Abstractions/Persistence/Users/UserReadModel.cs`) — a flattened DTO the Read Service assembles via one no-tracking `Select` projection over `User` + its `Profile`/`Contacts`/`RoleAssignments.Role` navigations, since Application never sees the aggregate itself. `Email`/`PhoneNumber` resolve to the primary `UserContact` of that type (`ContactType.Email`/`.Phone`); `Roles` resolves to the `Key` of every currently-effective `UserRoleAssignment.Role` (`UserRole`, User's own segmentation aggregate — see "Denormalized Roles" below for why this is *not* the same concept as Auth's Identity roles). `UserRepo` (`User.Persistence/Contexts/Users/Repositories/`) implements the generic `BuildingBlock.Persistence.Repository.IRepository<User>` in full via an empty `IUserRepository` marker. Per the tracker's Course Correction: `CreateUserHandler`/`UpdateUserHandler` own `IUnitOfWork.ExecuteTransactionAsync` themselves and call `IUserWriteService.CreateAsync`/`UpdateProfileDetailsAsync` (intent-named, not a delegate), which just stage the repo mutation; `DeleteUserHandler`/`OnUserInitiatedHandler`'s methods commit via bare `SaveChangesAsync` inside the `WriteService` itself. `User.Create` gained an optional `Guid? id` override solely so `SyncFromAccountInitiationAsync` can mint the User row with the *same* id as the Account Auth already created — the two rows are correlated by sharing an id, not a separate foreign key. Within `NovaCore.User.Persistence.*` namespaces, the bare type name `User` collides with the `NovaCore.User` namespace segment itself (CS0118) — every Persistence file uses the `UserEntity` alias (`GlobalUsings.cs`) instead of `User` for this reason; Application avoids the same collision by never being nested under a `...Users` segment that shadows it.

## Denormalized Roles

`CreateUserCommand.Roles`/`UserProfileCreatedIntegrationEvent.Roles` (`string[]`) are **Auth's own Identity role names** (`AccountRole`/`Role.Name`, e.g. `"Root"`/`"Admin"`/`"User"`) passed straight through from the admin-facing `CreateUser` endpoint to Auth's `UserCreatedIntegrationEventConsumer`, which assigns them to the newly-created `Account`. This is a *different* concept from `User.Domain`'s own `UserRole`/`UserRoleAssignment` (an independent business-segmentation aggregate local to User service — e.g. customer-support bundles — surfaced read-only via `UserReadModel.Roles`/`/users/search`'s `role` filter). The two happen to share the word "Roles" but nothing else. `CreateUserHandler` used to validate the incoming string array against `AppRoleConstant.SupportedRoles` and enforce "only Root may grant Admin" — both removed 2026-08-04 (User service has no authority over which Auth role names are valid or grantable; that belongs to Auth's own Role/Position admin surface, which this endpoint should eventually delegate to rather than re-implement). **Not yet functional**: nothing currently populates `CreateUserCommand.Roles`/`RoleIds` from a real admin-facing Role/Position picker — wiring that (once Auth exposes the right admin API) is tracked as future work, not started.

## Known issues

- Mapster registered but unused, same as Auth — see [04-coding-rules.md](../04-coding-rules.md#mapping).
- `DeleteUserCommand`/`DeleteUserHandler` (`User.Application/Features/Users/Commands/DeleteUser/`) are dead code — confirmed via repo-wide grep, nothing anywhere constructs or sends a `DeleteUserCommand`. The real deletion path is `UserAccountDeletionIntegrationEventConsumer` → `OnUserDeletionEvent` → `OnUserDeletionHandler` → `IUserWriteService.DeleteWithNoTrackingAsync`. Any future work touching deletion semantics (cache/search invalidation, audit, etc.) must target that path, not the unused command — found and worked around during the 2026-07-28 search/cache/gRPC epic (`docs/tasks/2026-07-28/`), not yet cleaned up.
- Elasticsearch's index rebuild (`POST /users/search/rebuild`) is a blocking drop+recreate with no blue/green alias swap, same accepted limitation as Product's equivalent endpoint (see [reference/search.md](../reference/search.md#future-extension-points)).
