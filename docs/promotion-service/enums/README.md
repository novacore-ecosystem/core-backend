# Promotion Service — Enums

**Scope:** Catalogue of every `Promotion.Domain` enum, updated as each is introduced (step 6 of [../entities/entity-implementation-strategy.md](../entities/entity-implementation-strategy.md)).

## Phase 2.5 consolidation

The Domain Standardization Review found `LoyaltyProgramStatus`, `RewardProgramStatus`, `RecommendationProgramStatus`, `GiftProgramStatus` were all byte-for-byte identical (`Draft`/`Active`/`Paused`/`Expired`/`Archived`, same order) and merged them into one shared `ProgramStatus`, used by all four aggregate roots. Every other Status/Type enum in this service has a genuinely distinct value set and was left as its own enum.

## Phase 2.6 correction

The Final Domain Correction pass scanned every entity for string properties that actually represent a finite, closed set of states and converted them to enums (eliminating "accidental string-based domain enumerations" left over from phase briefs that omitted an explicit enum). Nine new enums were added: `PromotionRuleGroupOperator`, `PromotionConditionOperator`, `PromotionTargetType` (placeholder), `PromotionBenefitType` (placeholder), `PromotionConstraintType` (placeholder), `PromotionUsageScope`, `ReservationStatus`, `ApprovalDecisionType`, `ApprovalStepStatus`, `ValidationResultStatus`, `SimulationResultStatus`. Genuinely open-ended classifier fields (`RuleType` on `PointRule`/`RecommendationRule`/`BundleRule`/`PromotionValidationPolicy`, `ApprovalWorkflow.WorkflowType`) were deliberately left as `string` — they are extensible plugin-style taxonomies, not closed sets, and converting them would invent a business rule the design never specified.
