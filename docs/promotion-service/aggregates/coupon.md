# Coupon Aggregate

**Scope:** Domain-layer facts for the `Coupon` aggregate, implemented Phase 2.2. Structural only — no business rule (eligibility, redemption enforcement, approval workflow) is implemented yet.

## Aggregate boundary

`Coupon` (`Promotion.Domain/Entities/Coupons/Coupon.cs`) is the aggregate root — `AggregateRoot<Guid>`, `IAuditable`, `ITenantEntity`. It always belongs to a `Promotion` (`PromotionId`, mandatory), optionally to a `Campaign` (`CampaignId`) and a `CouponBatch` (`BatchId`) — unlike Campaign/Promotion, the phase brief explicitly requested navigation *object* properties for `Promotion`/`Campaign`/`Batch`, not just FK ids, so all three are nullable object references here. It owns, via `ICollection<T>` navigation + internal construction (Rule 3): `CouponReservation`, `CouponUsage`, `CouponHistory`, `CouponVersion`.

`CouponBatch`, `CouponCode` (the entity), and `CouponApproval` are **not** part of this aggregate's owned navigation graph — the brief's own Navigation list (`Promotion`, `Campaign`, `Batch`, `Reservations`, `Usages`, `History`, `Versions`) omitted a `Codes` collection and `CouponApproval` entirely, so:
- `CouponBatch` — independent lifecycle (many coupons/codes can reference one batch), public `Create`, referenced by `Coupon.BatchId`.
- `CouponCode` — individually issued/redeemable codes under a coupon (e.g. from a batch import) — distinct from `Coupon.Code` (the coupon's own/template code). Public `Create`, related by `CouponId`/`BatchId` only.
- `CouponApproval` — minimal structural placeholder, same deferral as `CampaignApproval` (real workflow is a later Phase 2.x — Approval + Validation + Audit).

## `CouponCode` name collision — resolved in Phase 2.5, not just worked around

`CouponCode` is both an entity (`Entities/Coupons/CouponCode.cs`) and (until Phase 2.5) a per-aggregate Value Object (`ValueObjects/CouponCode.cs`). Phase 2.2 worked around the collision with file-local (`CouponCodeVo`) and global (`CouponCodeEntity`) aliases, since `Coupon.cs` sits in the *same* namespace as the `CouponCode` entity and C# resolves a bare name against same-namespace declarations before any `using`/global-using import is even considered. The Phase 2.5 Domain Standardization Review **removed the collision at its root**: the per-aggregate Code VO was consolidated into the shared `EntityCode` (see [../value-objects/README.md](../value-objects/README.md)), so the VO no longer shares the entity's name — both alias workarounds were deleted.

## Enums

- `CouponStatus` — Draft/PendingApproval/Approved/Scheduled/Active/Paused/Expired/Cancelled/Archived (all 9 values given explicitly by the phase brief — no invented taxonomy this time).
- `CouponVisibility` — Public/Private/Assigned/Hidden (given explicitly).
- `CouponType` — Shared/Unique/AutoGenerated/Imported (given explicitly).

## Value Objects

- `EntityCode` (shared, consolidated Phase 2.5) — used by `Coupon.Code` and the `CouponCode` entity's own `Code` field.
- `Period` (shared, consolidated Phase 2.5, reserved) — `Coupon` itself keeps flat `StartTime`/`EndTime`/`TimeZone` scalars per its literal Properties list.
- `CouponUsageLimit` — bundled `MaxUsage`/`MaxUsagePerUser` pair, reserved (`Coupon` itself keeps them as flat scalars per its literal Properties list). Unique shape, not merged with anything.

## Indexes (design only — written in Phase 3)

- `(Code)` unique · `(Status)` · `(Visibility, Status)` · `(PromotionId)` · `(CampaignId)` · `(StartTime, EndTime)` · `(TenantId, Code)` unique
- `CouponUsage`: `(CouponId)`, `(UserId)`, `(OrderId)`

## Phase 2.6 correction

`CouponReservation.Status` converted from a free `string` (default `"Reserved"`) to the new `ReservationStatus` enum (Reserved/Released/Expired/Consumed). `Coupon.PromotionId`/`CampaignId`/`BatchId` navigations, `EntityCode`/`Period`/`CouponUsageLimit` usage, and `CouponStatus` (no `Rejected` value added — `Cancel()` already provides a working exit path from `PendingApproval`, so adding a new terminal status would invent an unrequested lifecycle state) were all re-verified and left unchanged.

## Reconciliation notes

Same as Campaign/Promotion — no `EntityData`/`UpdateData`/`CouponTranslationData` wrapper types created; every `Create`/update/translate method takes flat parameters (Domain Rule 2).
