# Task 9: Promotion Service — Phase 4.4 Coupon Lifecycle / Redemption Foundation

**Status:** Done — fourth Phase 4 (Application/CQRS/API) prompt. Phase 4 remains in progress; no Promotion Engine (rule evaluation, discount calculation, stacking) exists yet.
**Category:** Coupon lifecycle — validate-before-redeem and the real redemption operation, using the existing Coupon Domain model (`RecordUsage`, `CouponUsage`) exactly as designed.

## What was done

**Application layer — shared eligibility rule** (`Promotion.Application/Features/Coupons/Shared/CouponRedemptionEligibility.cs`, new): `Evaluate(Coupon, int userUsageCount)` checks `IsEnabled`, `Status == Active`, the `StartTime`/`EndTime` window, `MaxUsage`, and `MaxUsagePerUser` — the only fields the Coupon Domain exposes for this. `Coupon.RecordUsage`'s own doc comment ("no eligibility/limit enforcement lives here") explicitly disclaims this as a Domain responsibility, confirming it genuinely belongs in Application rather than being logic pulled up out of the Domain. Both `ValidateCouponHandler` and `RedeemCouponHandler` call this same method — the rule set is defined exactly once.

**Validation** (`Queries/ValidateCoupon/`, new): `ValidateCouponQuery(Code)` → `ValidateCouponHandler`. Read-only, never mutates. Resolves the acting user via `ICurrentUserService.GetUserId()` (matching `AddCartItemHandler`'s precedent — not a Command/Query field). A missing or currently-invalid Coupon returns `ValidateCouponResponse(CanProceed: false, Reason: "...")` at 200 OK — not an exception — since "is this code usable right now?" is a normal question with a normal negative answer, not a client error.

**Redemption** (`Commands/RedeemCoupon/`, new): `RedeemCouponCommand(Code, OrderId?)` → `RedeemCouponHandler`. Establishes usage/claim state only — never a discount amount, order total, or stacking outcome (explicitly out of scope). Re-runs the same `CouponRedemptionEligibility.Evaluate` live on every attempt rather than trusting a prior `ValidateCoupon` call (a validation result can go stale between the two calls). Calls `Coupon.RecordUsage(userId, orderId)` — the Domain's own existing usage-recording method — via a new `ICouponWriteService.RedeemAsync`, persisting into `CouponUsage`, the aggregate's **existing** Phase 2.2 redemption entity. No new entity was created; the issuing prompt's own instruction was to stop and document a missing capability rather than invent one, and `CouponUsage` already existed.

**Concurrency**: `Coupon` already carries PostgreSQL `xmin`-based optimistic concurrency (`CouponConfig.ConfigureCommonFields()`, wired since Phase 3.1) — no new concurrency token added. `EfUnitOfWork.ExecuteTransactionAsync` (BuildingBlock, pre-existing) already translates a `DbUpdateConcurrencyException` into the Application-layer `ConflictException`. `RedeemCouponHandler` wraps its entire "reload Coupon → re-check eligibility → mutate → save" sequence in a new `OptimisticConcurrencyRetry` (`Promotion.Application/Abstractions/Persistence/OptimisticConcurrencyRetry.cs`) — cloned from Inventory's own local helper of the identical name and shape (confirmed not a shared `BuildingBlock` type, so each service that needs this pattern keeps its own copy, same as Inventory's). This exactly mirrors `DeductStockHandler`'s structure, the only existing precedent in the platform for "counter under concurrent contention, retry via re-evaluation of fresh state."

**Idempotency, two layers, matching `CreatePayment`'s precedent**: (1) the `RedeemCoupon` endpoint requires the platform's existing `Idempotency-Key` header via `.RequireIdempotency()` — the same HTTP-level middleware/response-cache mechanism (`IdempotencyMiddleware`, already active in Promotion's pipeline since bootstrap) every other idempotent write endpoint uses (`CreatePayment`, `CreateOrder`, `CreateUser`, `CreateProduct`). (2) `RedeemCouponHandler` additionally checks for an existing `CouponUsage` matching the same (Coupon, User, Order) natural key and replays it instead of redeeming a second time — permanent, not TTL-bound like the HTTP cache, and works whenever a caller supplies `OrderId` (the expected case once OrderService integrates). No synthetic `IdempotencyKey` field was added to `CouponUsage` — the Domain was not touched this phase, unlike Payment's own `IdempotencyKey` field on the `Payment` aggregate root (Payment's placement doesn't transfer directly to Coupon, since a Coupon is reused across many redemptions rather than created once per request — `CouponUsage`'s own natural key does the equivalent job without a Domain change).

**Persistence layer**: `ICouponReadService` gained `GetByCodeAsync(code, ct)` (Code, not the internal `CouponId`, since a checkout-flow caller has the code, not the GUID — same identifier Phase 4.3's search already made the public-facing one) and `GetUsagesByCouponAndUserAsync(couponId, userId, ct)` (backs both the `MaxUsagePerUser` check and the idempotency check with one query). `ICouponWriteService` gained `RedeemAsync(couponId, userId, orderId, ct)` — stages only, `RedeemCouponHandler` owns `ExecuteTransactionAsync`, same split `UpdateDetailsAsync` uses. No entity-specific repository method was needed — `ICouponRepository`'s inherited `UpdateAsync(id, Action<Coupon>, ct)` already satisfies the mutation.

**Errors**: zero new exception types. `NotFoundException` (Coupon not found by code), `ForbiddenException` (no current user — matches `AddCartItemHandler`/`ClearCartHandler` precedent), `BusinessRuleException` (Coupon not currently redeemable). One small additive extension to the shared `MessageCode` enum (`BuildingBlock.Domain.Enums.MessageCode`, `src/BuildingBlocks/BuildingBlock.Domain/Enums/MessageCode.cs`): a new "Promotion Service (900-999)" range — `CouponDisabled = 900`, `CouponNotActive = 901`, `CouponUsageLimitReached = 902` — the same per-service-numeric-range convention already established for Product (400s), Inventory (500s), Order (600s), User (700s), Payment (800s). This is the first BuildingBlock file this Promotion Service build has touched; the change is purely additive (new enum members only), so it cannot break any existing consumer.

**API layer**: `GET /coupons/validate?code=...` (`ValidateCoupon.cs`, new) and `POST /coupons/redeem` (`RedeemCoupon.cs`, new, with `Headers([...IdempotencyKey])` + `.RequireIdempotency()`, matching `CreatePayment`'s exact endpoint shape). Both `.RequireAuthorization()`, consistent with every other Coupon endpoint (no anonymous-access precedent exists anywhere in the platform to justify deviating here).

**Deliberately not implemented, per this phase's explicit scope**: Coupon Reservation (`Coupon.AddReservation`/`ReleaseReservation` already exist on the Domain from Phase 2.2, but neither the issuing prompt's concrete requirements (Sections 5-26) nor its final-report checklist (Section 35) named Reservation as a deliverable — only Validation and Redemption were required, so Reservation stays an available-but-unused Domain capability, the same kind of deliberate boundary Phase 4.2 drew around `AssignCampaign`/`AssignBatch`); Elasticsearch sync from the redemption Handler; any Order/User service call; any discount/stacking/eligibility-beyond-the-Coupon-itself logic.

**Build**: one `dotnet build` of `Promotion.API.csproj` after the full feature landed. **Succeeded, 0 errors** on the first attempt, no new warnings introduced (verified via a non-incremental rebuild — same pre-existing warning set as Phase 4.3).

## Objective

Establish the real Coupon lifecycle foundation — validate-before-redeem and the redemption operation itself — using the existing Domain model, transaction/concurrency/idempotency infrastructure, and error-handling conventions exactly as designed, without implementing any part of the Promotion Engine (discount calculation, stacking, eligibility beyond the Coupon's own state).

## Scope

**Built/changed this task:** 1 new shared Application file (eligibility rule), 4 new CQRS feature files (Validate query+handler, Redeem command+handler), 1 new Application infrastructure file (`OptimisticConcurrencyRetry`) + its DI registration, 2 Persistence Service interfaces extended, 2 Persistence Service implementations extended, 2 new Minimal API endpoints, 1 small additive extension to the shared `BuildingBlock.Domain.Enums.MessageCode` enum, 1 CQRS strategy doc section, 2 other doc updates.

**Explicitly not built:** Coupon Reservation wiring, any Promotion Engine logic, any cross-service (Order/User) call, any Elasticsearch synchronization, any new exception type, any new concurrency/idempotency abstraction beyond what already existed platform-wide or what Inventory's own precedent already established.

## Dependencies

Phase 4.2 (Task 7) — the Coupon Management foundation and `ICouponReadService`/`ICouponWriteService` this phase extends. Phase 3.1 — the `xmin` concurrency column this phase relies on. Inventory's `DeductStockHandler`/`OptimisticConcurrencyRetry` — the only existing platform precedent for "counter under concurrency, retry-with-refetch," cloned rather than re-derived. Payment's `CreatePayment` — the only existing precedent for the two-layer idempotency shape.

## Estimated complexity

Medium-large — the state-changing redemption operation required reasoning carefully through concurrency (xmin + retry), idempotency (HTTP header + natural-key), and error-convention reuse (MessageCode extension) simultaneously, even though no new entities or major abstractions were introduced.

## Risks

- The natural-key (Coupon+User+Order) idempotency check in `RedeemCouponHandler` only applies when a caller supplies `OrderId`. When `OrderId` is omitted, only the HTTP-level `Idempotency-Key` middleware (TTL-bound) protects against a duplicate redemption from a very late retry. Flagged here so this isn't mistaken for a gap missed rather than a documented, deliberate limitation given the Domain wasn't extended with a synthetic idempotency field this phase.
- `GET /coupons/validate`/`POST /coupons/redeem` will behave correctly against a real database today (unlike Phase 4.3's search, which is still wired to an empty, unsynchronized Elasticsearch index) — Validate/Redeem read/write PostgreSQL directly, not the search index.
- Coupon Reservation remains unwired — a future phase that wants a "hold a Coupon during checkout" step will need its own Application feature; the Domain methods (`AddReservation`/`ReleaseReservation`) are ready and unchanged.
