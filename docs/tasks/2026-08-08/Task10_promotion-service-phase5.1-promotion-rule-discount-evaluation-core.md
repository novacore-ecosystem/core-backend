# Task 10: Promotion Service — Phase 5.1 Promotion Rule & Discount Evaluation Core

**Status:** Done — first Phase 5 (Core Business APIs) prompt. **Phase 4 (Application/CQRS/API) is fully closed.** No Promotion Engine beyond this phase's own scope exists yet (no Coupon-/Campaign-triggered evaluation, no full stacking optimization, no Rule/Condition interpretation).
**Category:** The first real Promotion business engine work — Promotion Management, Approval, and the core discount-evaluation API.

## What was done

**Domain change #1 — Approval wiring** (resolved via AskUserQuestion before writing any code): `PromotionStatus` has only `Draft/Active/Paused/Expired/Cancelled` — no `PendingApproval`/`Approved`/`Rejected` states — and no `PromotionApproval` entity exists, yet the issuing prompt required real Submit/Approve/Reject APIs and "do not allow an unapproved Promotion to become Active." Presented three options to the architect (wire the existing general-purpose `ApprovalWorkflow` aggregate; add a minimal in-aggregate flag; skip approval this phase) and the architect chose wiring `ApprovalWorkflow` — the same aggregate Campaign's/Coupon's own approval placeholders (Phase 2.1/2.2) already deferred to, never wired to anything until now. Added `Promotion.ApprovalWorkflowId`/`ApprovalWorkflow` (nullable reference, id-only — Promotion never calls `ApprovalWorkflow`'s own methods directly, since they're independent aggregate roots) and `Promotion.IsApproved`, plus `SubmitForApproval(Guid)`/`MarkApproved()`/`MarkRejected()`. `Activate()` now additionally guards on `IsApproved`. Since `PromotionStatus` has no separate Scheduled state, "Approve" both approves the linked workflow and activates the Promotion in the same operation — there is no separate Activate endpoint.

**Domain change #2 — Constraint taxonomy fill-in**: `PromotionConstraintType` was explicitly marked "TODO structural placeholder... confirm/replace when the design is available" since Phase 2 and only had `MinimumOrderAmount`/`MinimumQuantity`/`CustomerSegment`/`ProductCategory`/`PaymentMethod`. Added `MaximumOrderAmount`/`MaximumQuantity`/`MaximumDiscountAmount` — exactly the fields Sections 7/9/16 of the issuing prompt name by name, filling the placeholder's own stated invitation rather than escalating (unlike the Approval question, this one had no genuine model conflict — it's an explicitly-flagged, additive-only gap).

**Persistence**: `PromotionConfig` gained `IsApproved` + the `ApprovalWorkflowId` FK (`.WithMany()`, no reverse collection — same shape as the existing `Campaign` relationship). `IPromotionReadService`/`PromotionReadService` gained `GetByIdAsync` (with Benefits/Targets/Constraints/StackingPolicy/Translations included), `SearchAsync` (pagination), `GetEvaluationCandidatesAsync` (enabled + Active + currency-matched + `ExecutionMode.Automatic`, with the child collections evaluation needs), `GetExclusionsAsync` (`PromotionExclusion` has no `Promotion` navigation collection by design, so it's queried directly). `IPromotionWriteService`/`PromotionWriteService` gained Create/UpdateDetails/Enable/Disable/Cancel/SubmitForApproval/Approve/Reject/AddExclusion — the last one injects `PromotionDbContext` directly (not `IPromotionRepository`) because `PromotionExclusion` is a pure-mapping, composite-key entity with a public (non-`internal`) `Create` and no owning navigation collection, so it cannot go through the generic `IRepository<Promotion, Guid>` binding. `IApprovalWorkflowReadService`/`IApprovalWorkflowWriteService` got their first real methods (`GetByIdAsync`; `CreateAsync`/`ApproveAsync`/`RejectAsync`, all stage-only — see below).

**Application — Promotion Management** (`Features/Promotions/{Commands,Queries}/`): `CreatePromotion` (Handler constructs `Promotion.Create(...)` directly, then attaches any initial Benefits/Targets/Constraints/StackingMode — set once, at creation, this phase has no endpoint to change them afterward), `GetPromotion`, `ListPromotions` (`PaginatedResult<T>`, mirrors `ListCoupons`), `UpdatePromotion` (Name/Description/Schedule/Priority only, same scope boundary `UpdateCoupon` drew), `EnablePromotion`/`DisablePromotion`/`CancelPromotion` (`Cancel()` — Section 27's "Delete" maps to the Domain's own soft-cancel, never a physical delete).

**Application — Approval** (`SubmitPromotion`/`ApprovePromotion`/`RejectPromotion`): the first Handlers in Promotion Service to orchestrate two independent aggregate roots in one transaction. `SubmitPromotionHandler` creates+submits a new `ApprovalWorkflow`, then links it via `Promotion.SubmitForApproval`. `ApprovePromotionHandler`/`RejectPromotionHandler` load the Promotion to get its `ApprovalWorkflowId`, then approve/reject the workflow and update the Promotion, both inside one `IUnitOfWork.ExecuteTransactionAsync`. Because of this, `IPromotionWriteService`/`IApprovalWorkflowWriteService`'s Submit/Approve/Reject-shaped methods stage only (no bare `SaveChangesAsync`) — the Handler, not either Persistence Service, owns the single transaction spanning both aggregates.

**Application — Evaluation** (`EvaluatePromotionsQuery` → `EvaluatePromotionsHandler`, `POST /promotions/evaluate`): a single deterministic pass —
1. Load candidates (`IsEnabled`, `Status == Active`, matching `Currency`, `ExecutionMode.Automatic`).
2. Filter by time window (`StartTime <= now < EndTime`).
3. Match `PromotionTarget` rows: `Product`/`Sku`/`Category` narrow to matching order items; `Customer` gates on the caller's `UserId`; `Cart`/`Order`/no targets means the whole order.
4. Evaluate `PromotionConstraint` rows the request actually carries data for (`MinimumOrderAmount`/`MaximumOrderAmount`/`MinimumQuantity`/`MaximumQuantity`/`ProductCategory`; `MaximumDiscountAmount` caps the discount rather than gating eligibility). `CustomerSegment`/`PaymentMethod` constraints are configurable but **not evaluated** — the minimal evaluation request (Section 14) carries neither field. Documented, not silent.
5. Compute discount from `PromotionBenefit` rows (`PercentageOff`/`FixedAmountOff` real; `FreeShipping`/`FreeGift` report a zero monetary amount — no shipping-cost/gift-value data modeled).
6. Resolve a stackable subset: sort by `Priority` descending then `CreatedAt` ascending, then a deterministic greedy walk respecting `PromotionStackingPolicy.Mode` (`NotStackable` stops everything after it; `StackWithSameType` requires the same `PromotionType` as everything already applied) and explicit `PromotionExclusion` pairs (always block, regardless of mode) — a baseline pass, not the full optimization algorithm the issuing prompt explicitly defers to a later phase.
7. Return `EvaluatePromotionsResponse(IsEligible, TotalDiscountAmount, AppliedPromotions[])` — never a final Order total (OrderService's own responsibility), with each `AppliedPromotionResult` carrying an explicit `ApplyOrder` int so the caller doesn't have to infer ordering from array position.

No OrderService/ProductService/InventoryService dependency of any kind — the caller supplies the order snapshot (`EvaluatePromotionsQuery`'s `Items`) directly. `PromotionRule`/`PromotionRuleGroup`/`PromotionCondition` (the Domain's generic Field/Operator/Value mechanism) remain configurable but are **not interpreted** by the evaluation engine — doing so generically would be exactly the "generic expression engine" the issuing prompt explicitly forbade (Section 9); only the small, fixed `PromotionConstraint`/`PromotionTarget` enums are evaluated.

**API layer** (`Promotion.API/Endpoints/Promotion/`, 12 new endpoints): `POST /promotions`, `GET /promotions/{id}`, `GET /promotions`, `PUT /promotions/{id}`, `POST /promotions/{id}/enable`, `POST /promotions/{id}/disable`, `DELETE /promotions/{id}`, `POST /promotions/{id}/submit`, `POST /promotions/{id}/approve`, `POST /promotions/{id}/reject`, `POST /promotions/{id}/exclusions/{excludedPromotionId}`, `POST /promotions/evaluate`. All `.RequireAuthorization()`, matching every other Promotion Service endpoint.

**Errors**: reused `NotFoundException`/`BusinessRuleException` throughout — no new exception types.

**Documentation**: new [promotion-engine/promotion-engine-core.md](../../promotion-service/promotion-engine/promotion-engine-core.md) — concise business-capability summary only (lifecycle/approval, targeting, conditions/discount, priority/stacking, evaluation, explicit not-implemented list), per this phase's own instruction not to re-explain architecture already documented elsewhere. Added a short "Phase 5.1" section to [cqrs/cqrs-strategy.md](../../promotion-service/cqrs/cqrs-strategy.md) recording only the cross-aggregate-transaction shape note. Updated `README.md` and `planning/PROGRESS.md`.

**Build**: one `dotnet build` of `Promotion.API.csproj` after the full feature landed. Two real compile errors were found and fixed (my own helper methods declared `IReadOnlyCollection<T>` parameters where the entity's actual navigation properties are `ICollection<T>`). **Final build succeeded, 0 errors**, no new warnings (verified via a non-incremental rebuild against the same pre-existing 20-warning baseline — `Promotion`'s and `ApprovalWorkflow`'s own Read/Write Persistence Service `CS9113` "unread parameter" warnings are gone now that they do real work).

## Objective

Implement the core Promotion business engine foundation — real Promotion Management, an Approval flow gated correctly against Activation, and a deterministic discount-evaluation API — using the existing Domain model as the source of truth, escalating only the one genuinely load-bearing contradiction (approval model) rather than guessing, and staying within the explicit scope boundary (no Campaign/Coupon/Voucher/Point/Gift/stacking-optimization/OrderService/InventoryService work).

## Scope

**Built/changed this task:** 2 Domain files (enum extension, `Promotion.cs` approval wiring), 1 Persistence config edit, 4 Persistence Service interface files + 4 implementations, 11 new Application CQRS feature folders (~24 files), 12 new Minimal API endpoints, 1 new business-capability doc, 2 other doc updates.

**Explicitly not built:** Coupon-/Campaign-triggered evaluation, Promotion Rule/RuleGroup/Condition CRUD or interpretation, Product Gift configuration, child-collection (Benefits/Targets/Constraints) updates after creation, the full stacking optimization algorithm, any OrderService/InventoryService/ProductService integration, Campaign/Voucher/Point/Product Set/Up-Sell/Cross-Sell/Broadcast/Reward Distribution.

## Dependencies

Phase 2.1/2.4 (Campaign/Coupon Approval placeholders, `ApprovalWorkflow` aggregate) — the approval infrastructure this phase finally wires up. Phase 3.1 (`PromotionConfig`, `xmin` concurrency) and Phase 4.2 (`CouponRedemptionEligibility`-style shared-rule pattern, cloned in spirit for the evaluation engine's own structure).

## Estimated complexity

Large — the single biggest Application-layer phase so far: 12 endpoints, a cross-aggregate transactional Approval flow, and a genuinely non-trivial deterministic evaluation algorithm, all built and compiling clean on essentially the first pass.

## Risks

- The evaluation engine's stacking pass is explicitly a baseline greedy algorithm (Priority + StackingMode + PromotionExclusion), not a true optimization search — flagged in both `promotion-engine-core.md` and here so a future session doesn't mistake "not maximizing total discount across all valid combinations" for a bug.
- `CustomerSegment`/`PaymentMethod` constraints are configurable via `CreatePromotion` but silently unenforced by evaluation — an admin configuring one will not see it take effect until a future phase extends `EvaluatePromotionsQuery`'s context. Documented in three places (code comment, `promotion-engine-core.md`, this file) to reduce the chance of this being mistaken for an oversight.
- The `ApprovalWorkflow` wiring only covers `Promotion` — `CampaignApproval`/`CouponApproval`'s own placeholders remain unwired, exactly as before this phase (out of scope, not touched).
